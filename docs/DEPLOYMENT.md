# Deployment

Two supported shapes. Pick one.

Supabase is a **database + storage** service, not a Node host: it cannot run
`server.js`. The Express API needs a Node runtime. So the pieces land like this:

| Piece | Runs on | Why |
|---|---|---|
| Pages (`public/`) | **Vercel** | Static files on a CDN; free, fast, HTTPS, custom domain |
| API (`server.js`) | **Render / Railway / Fly / a VPS** | Needs a long-lived Node process (connection pool, image processing) |
| Postgres + images | **Supabase** | Managed database and object storage |

| Shape | Frontend | API | Use when |
|---|---|---|---|
| **A — single service** (simplest) | Served by Express | Same Express process | You want one URL and no CORS |
| **B — split** (what you asked for) | Vercel | Render (or any Node host) | Frontend on Vercel's CDN, API elsewhere |

## Shape A — API on Render (recommended for you)

The repository ships `render.yaml`, a Render **Blueprint**. It declares the whole
service, so you do not have to remember any setting.

### Node version

`package.json` pins `"node": ">=20 <23"`. Without an upper bound, Render resolves
`>=20` to the newest major it offers — on the first deploy it chose **Node 26**,
which nothing here has been tested against (native modules: sharp, pg). Both
Node 20 and 22 are exercised by CI on every push; 22 is the recommended target.

### If the deploy says `tenant/user <ref> not found`

The pooler identifies your project by the **host** it is reached on, so the wrong
cluster answers "tenant/user not found" even when the ref is correct. Run the
probe from your machine — it tries every candidate and prints the one that works:

```bash
node scripts/check-db.js 'postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres'
```

```
127.0.0.1:49546                            ✓ connected in 57 ms
aws-1-ap-south-1.pooler.supabase.com:5432  ✗ timeout expired
aws-0-ap-south-1.pooler.supabase.com:5432  ✗ tenant/user ... not found

USE THIS AS DATABASE_URL:
postgresql://postgres.<ref>:<PASSWORD>@aws-1-ap-south-1.pooler.supabase.com:5432/postgres
```

It distinguishes the three failure modes: *tenant/user not found* (wrong host or
paused project), *password authentication failed* (wrong password) and *timeout*
(no route — usually the IPv6-only direct host).

### Environment variables

`render.env.example` in the repository root is a paste-ready block for Render's
**Environment → Add from .env**. Every variable is annotated with where its value
comes from; 41 in total, of which only ten need your input and two are secrets
Render can generate.

### One-time deploy

1. Render dashboard → **New → Blueprint** → connect this repository → **Apply**.
   Render creates `campusconnect-api` with:
   - build `npm ci`
   - start `npm run migrate && npm start` (migrations are idempotent, so every
     boot is safe and a broken database fails the deploy loudly)
   - health check `/api/health`
   - `NODE_ENV=production`, `TRUST_PROXY=1`, `STORAGE_DRIVER=supabase`
   - `JWT_SECRET` and `OTP_PEPPER` **generated by Render** — you never see them,
     and they are never in the repo
2. Render asks for the values marked `sync: false`. Have these ready:

| Variable | Where to get it |
|---|---|
| `DATABASE_URL` | Supabase → Settings → Database → Connection string (URI) |
| `ALLOWED_EMAIL_DOMAINS` | the confirmed university domain, e.g. `saiuniversity.edu.in` |
| `APP_URL` | your Vercel URL, e.g. `https://campusconnect.vercel.app` |
| `CORS_ORIGINS` | the same Vercel URL |
| `MAIL_FROM`, `SMTP_HOST`, `SMTP_USER`, `SMTP_PASS` | your mail provider |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Settings → **API Keys** (`sb_secret_…` on new projects, `service_role` JWT on older ones — both work) |

3. Wait for the first deploy, then open `https://<service>.onrender.com/api/health`.
   It must return `{"ok":true,"database":{"connected":true}}`. If it does not, the
   log line names the missing variable or the failed connection.

### Creating the administrator on Render

Render's **free plan has no shell**. Two ways around it:

- **SQL Editor (works on every plan):** run `node scripts/hash-password.js`
  locally, then paste the SQL it prints into the Supabase SQL Editor. A ready
  template with the administrator's email already filled in lives at
  `db/supabase/create_admin.sql` — replace the hash placeholder and run it. If
  you forget, Postgres refuses the insert: the `users_password_hash_bcrypt`
  constraint only accepts a real bcrypt digest, so an unusable administrator
  cannot be created by accident.
- **Render Shell (paid plans):** `ADMIN_EMAIL=… ADMIN_PASSWORD=… npm run create-admin`.
- **One-off Job (paid plans):** create a Job from the same repository with
  command `npm run create-admin` and the admin variables added to its environment.

### Free-plan facts you should know before a campus launch

| Behaviour | What it means for you |
|---|---|
| The service **sleeps after ~15 minutes** of inactivity | The first request afterwards takes 30–60 s. Fine for a pilot; announce it, or upgrade before a campus-wide launch. |
| **Ephemeral disk** | `STORAGE_DRIVER=local` loses every photo on the next deploy. The blueprint sets `supabase` — keep it. |
| **No shell** | Use the SQL route or a Job to create the administrator. |
| **750 free instance-hours/month** | One always-on service fits; two do not. |

> Render's disk is **ephemeral**. With `STORAGE_DRIVER=local` every uploaded photo
> disappears on the next deploy — use Supabase Storage in production. This is the
> single most common way this app would look broken after a deploy.

## Shape B — Vercel frontend + Render API

### API on Render
Follow Shape A above. Note that `APP_URL` must be the **Vercel** URL, not the
Render one — the emails are built from it.

### Frontend on Vercel

**Set Root Directory to `public`.** That single setting is the difference
between a deploy and the error below.

```
Error: [BUILD_FAILED] No entrypoint found in output directory: "public".
Searched for: app.{js,cjs,mjs}, index.{js,cjs,mjs}, server.{js,cjs,mjs} …
```

Why it happens: the repository root contains `package.json`, `server.js` and
`express`, so Vercel classifies the project as a **Node backend**. It installs all
of the API's dependencies and then looks for a serverless function entrypoint
*inside* the output directory — which a folder of `.html` files cannot provide.
Pointing the project at `public/` removes the ambiguity: Vercel sees a folder of
static files, installs nothing and runs no build.

1. **Add New → Project** → import this repository.
2. **Root Directory → Edit → `public`**.
3. Framework Preset: **Other**. Build Command: **empty**. Output Directory:
   **empty**. Install Command: **empty** (there is nothing to install).
4. Deploy.

`public/vercel.json` travels with the folder and supplies clean URLs, the
`/admin` rewrite and the security headers (CSP, HSTS and
`Permissions-Policy: camera=(self)`, which the "Take photo" button needs).

Deploying the standalone `campusconnect-frontend.zip` instead works too — it has
no `package.json`, so Vercel treats it as static with no settings to change.

**Do not** leave Root Directory at the repository root: that is exactly the
configuration that produces the error above.

5. Before deploying, edit `public/assets/config.js`:

```js
window.CAMPUS_CONFIG = {
  apiBase: 'https://campusconnect-api.onrender.com',  // no trailing slash
  siteName: 'CampusConnect',
  university: 'Sai University',
};
```

4. On the API, allow the Vercel origin:

```
CORS_ORIGINS=https://campusconnect.vercel.app
```

5. `APP_URL` on the API must be the **Vercel** URL, not the Render URL: it is used
   to build the links inside verification emails.

```bash
APP_URL=https://campusconnect.vercel.app
```

6. Redeploy both after changing either value.

> In Shape B the API's Content-Security-Policy does not apply to pages served by
> Vercel. Vercel serves its own headers; if you need the same CSP there, add it in
> `vercel.json`.

### Storage buckets (Supabase)

Run `db/supabase/storage_setup.sql` in the Supabase SQL Editor. It creates both
buckets with the same size and MIME limits the API enforces:

| Bucket | Public | Used for |
|---|---|---|
| `item-images` | yes | Gallery photos |
| `claim-evidence` | **no** | Ownership proof on claims — signed URLs only |

Or create them by hand in **Storage → New bucket**, with exactly those names and
public/private settings, and a 5 MB limit with `image/webp, image/jpeg,
image/png` allowed.

### Creating the administrator

There is no public admin signup. Pick one of these:

**Option 1 — the script (recommended: it validates the domain and writes an audit entry)**

```bash
DATABASE_URL='postgresql://…' \
ADMIN_EMAIL='jaishubhakanth.m-29@scds.saiuniversity.edu.in' \
ADMIN_NAME='Jai Shubhakanth Mangali' \
ADMIN_PASSWORD='a-long-password-with-a-number' \
npm run create-admin
```

**Option 2 — SQL Editor only (no local checkout)**

```bash
node scripts/hash-password.js     # prints a bcrypt hash + the ready-made SQL
```

Paste the output into the Supabase SQL Editor.

Either way the administrator still receives an email OTP on every sign-in, and
the email must be on an allowed domain: `saiuniversity.edu.in` covers
`scds.saiuniversity.edu.in` because sub-domains are matched automatically.

After the first sign-in, rotate the password from **/admin/ → Security**. That
also signs out every other administrator session.

## Post-deploy verification (do this, do not assume)

Run these against the live URL in order. Each one proves a specific piece.

| # | Check | Expected |
|---|---|---|
| 1 | `GET /api/health` | `{"ok":true,"database":{"connected":true}}` |
| 2 | Open `/` | Gallery renders; counters show numbers, not dashes |
| 3 | Register with a **non**-university email | Rejected with a clear message |
| 4 | Register with a university email | "Enter your code" screen appears |
| 5 | Check the inbox | 6-digit code, branded email, link points at your https domain |
| 6 | Enter a wrong code | Rejected, attempts decrease |
| 7 | Enter the correct code | Signed in, dashboard loads |
| 8 | Log out, sign in again | Second OTP required |
| 9 | Report a found item **with a photo** | Listing appears in the gallery immediately |
| 10 | Open the listing as another account | No owner email visible anywhere in the page source |
| 11 | Claim the item | Finder receives an email; claim text is visible to the finder |
| 12 | Approve the claim | Item becomes "claimed"; a second approval attempt is refused |
| 13 | Confirm handover | Item becomes "returned" |
| 14 | Sign in at `/admin/` as a student | Refused |
| 15 | Sign in at `/admin/` as the admin | OTP, then console with real counters |
| 16 | Suspend a test account in the console | That account is signed out immediately |
| 17 | Redeploy the API, then open an old photo URL | Image still loads (proves object storage) |
| 18 | Admin → Audit log | Your moderation actions are listed with actor and time |

If #17 fails, `STORAGE_DRIVER` is still `local`.

## Environment checklist

- [ ] `NODE_ENV=production`
- [ ] `APP_URL` is the public **https** URL of the frontend
- [ ] `JWT_SECRET` and `OTP_PEPPER` are two different 64-character random values
- [ ] `ALLOWED_EMAIL_DOMAINS` contains the confirmed university domain
- [ ] `DATABASE_URL` uses `sslmode`/`DATABASE_SSL=true`
- [ ] `TRUST_PROXY=1` (Render/Vercel sit in front of the app)
- [ ] `CORS_ORIGINS` set only when the frontend is on another origin
- [ ] `STORAGE_DRIVER=supabase` with both buckets created
- [ ] `MAIL_TRANSPORT=smtp` with SPF/DKIM configured
- [ ] No secret appears in the repository, the frontend bundle or the logs
- [ ] `npm run migrate` ran on the deployed database
- [ ] Administrator created via `npm run create-admin`

## Rollback

1. Redeploy the previous build (Render keeps the last successful deploy; Vercel
   keeps every deployment).
2. Migrations are forward-only and additive, so an older build keeps working
   against the newer schema.
3. If a bad change corrupted data, restore the most recent `pg_dump`/Supabase
   backup — take one before any schema change.

## What is still missing for a real launch

These are honest gaps, not oversights:

- **Load testing.** The app has been exercised by an integration suite, not by a
  thousand concurrent students. Run a load test against staging before a
  campus-wide announcement.
- **Monitoring.** Add an uptime check on `/api/health` and an alert on 5xx rate.
- **Password reset.** Deliberately left to a later phase; the support path today
  is an administrator resetting the account.
- **Data retention policy.** Decide how long returned items and auth events are
  kept, and add a scheduled purge.
