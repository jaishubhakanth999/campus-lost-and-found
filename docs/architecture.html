CampusConnect — how the whole thing fits together

A lost & found portal for Sai University. Three deployables, one database, one rule: nothing is trusted until the university email is verified.

One request, step by step

What happens between a student tapping “Approve claim” and the database agreeing to it.

1
Browser sends the requestCookie-free: the JWT from localStorage goes in the Authorization header.
2
helmet + CORS + rate limitSecurity headers, an explicit origin allow-list, and a per-user request budget.
3
authenticateVerify the JWT signature, then look the session row up in user_sessions. Logged out, expired, revoked or suspended → 401, immediately.
4
requireRole + zod validationIs this an administrator endpoint? Is the body the right shape? Unknown fields are dropped; a query operator such as ?status[$ne]=open is a 400.
5
Service layer — the rules live here“Only the listing owner may decide a claim.” “An item cannot be marked returned while a claim is open.”
6
One transactionBEGIN → lock the claim and item rows → conditional UPDATE … WHERE status='open' → write the audit row → COMMIT. Half a change can never land.
7
Side effects after the commitEmail the claimant, then answer with JSON. A mail failure cannot roll back a decision.
Every response is JSON in one shape: { ok: true, … } or { error: { code, message, fields } }. The browser never parses HTML from the API, so a listing title containing <script> is inert data.
3

Signing in — two factors, then a session

The password is factor one. The 6-digit code sent to the university inbox is factor two. No token exists until both pass.

Email + password
→domain check
bcrypt compare
→code generated
OTP emailed
→user types it
JWT + session
1
Domain allow-listOnly @saiuniversity.edu.in and its sub-domains. A gmail address is refused before any password is checked.
2
Password checkbcrypt cost 12. Wrong password and unknown account return the identical message, so the form cannot be used to discover who has an account.
3
Code created, never stored plainly6 digits, valid 5 minutes, stored as an HMAC-SHA256 digest keyed with a server secret. Issuing a new code cancels the previous one.
4
Verification is atomicThe code is burned with UPDATE … WHERE consumed_at IS NULL. Two parallel requests cannot both succeed; five wrong tries destroy it.
5
Session row + JWTThe token carries a session id. Every later request checks that row, which is why logout and “suspend account” work instantly instead of waiting for the token to expire.
Forgotten password? A 64-character link, stored only as a digest, single use, 30 minutes. Using it signs every other session out — a stolen session does not survive a reset.

An item's life, and a claim's life

The two are linked on purpose: an item can only become “returned” through a completed claim, so the record always matches reality.

Item

open
→claim approved
claimed
→handover confirmed
returned
→archive
closed

Claim

pending
→owner approves
approved
→item collected
completed
rejected
withdrawn
…both terminal. A decided claim can never be re-decided (409), and approving one claim auto-rejects the rivals on that item.
This is the part the first version got wrong: the owner could not read the claim message, and a second approval could leave two “approved” claims on one item. Both are now impossible — the second approval fails its conditional update, and the message is on screen before the buttons.

The database — 8 tables

Constraints do the arguing, so a bug cannot quietly write nonsense: one account per email, one live code per purpose, one live claim per person per item, and a password hash that must really be a bcrypt digest.

users
  • email unique (lower-cased)
  • role student · admin
  • status active · suspended
  • is_email_verified
  • student_id · department · phone
  • created_at · updated_at
items
  • owner_id → users
  • type lost · found
  • status open · claimed · returned
  • images jsonb (references only)
  • search_vector (full-text)
  • expires_at · returned_at
claims
  • item_id → items
  • claimant_id → users
  • status pending → completed
  • message · evidence (private)
  • decided_by · decision_note
  • unique (item, claimant) while live
user_sessions
  • user_id → users
  • session_id (in the JWT)
  • login_at · logout_at
  • status active · logged_out · expired · revoked
  • ip · user_agent
otp_codes
  • user_id → users
  • purpose signup · login · admin_login
  • code_hash HMAC digest
  • attempts · max_attempts
  • expires_at · consumed_at
  • one live code per purpose
password_reset_tokens
  • user_id → users
  • token_hash digest only
  • expires_at · used_at
  • one live link per account
auth_events
  • user_id → users
  • event · outcome · reason
  • email · ip · user_agent
  • never a password, code or token
admin_audit_logs
  • actor_id → users
  • action · target_type · target_id
  • details (before/after)
  • ip · created_at
users 1 ─── ∞ items 1 ─── ∞ claims ∞ ─── 1 users · users 1 ─── ∞ sessions / otp_codes / reset_tokens / auth_events / audit_logs
Images are not in the database. The row holds a small reference ({key, url, width, height}); the bytes live in Supabase Storage. Claim evidence goes to the private bucket and is handed out only as a 5-minute signed link to the two people involved.
